# ETW без прав администратора: что доступно и какой ценой

**Дата:** 31.07.2026 · **Машина:** Windows 11 Pro 10.0.26200, обычная учётная запись (не
администратор) · **Метод:** `logman` + `tracerpt`, повышения не запрашивалось ни разу.

> В отчёте нет наблюдённых адресов. Трафик для проверки создавался специально и целиком
> на loopback: собственный процесс отправлял датаграммы на `127.0.0.1` на порты, выбранные
> для этого теста. Файлы захвата содержали несколько секунд общесистемной активности,
> просматривались только по этим самым константам и удалены. Имена провайдеров ETW и
> номера событий — публичные константы Windows, а не результат измерения.

Фаза 4 в PLAN.md опиралась на сеанс ETW `Microsoft-Windows-Kernel-Network`: таблицы ядра
не знают собеседника UDP-сокета, а игры играют именно по UDP. Спайк должен был ответить,
возможно ли это без администратора. Ответ: **возможно, но не тем провайдером, который был
записан в плане, и не бесплатно.**

## Итог

| Что | Обычный пользователь | + группа «Пользователи журналов производительности» |
| --- | --- | --- |
| Создать сеанс трассировки | **нет** (`0x80070005`), любой провайдер, любой режим | **да** |
| Увидеть чужие сеансы (`logman query -ets`) | список пуст | да |
| Провайдер `Microsoft-Windows-Kernel-Network` | нет | **нет** — отказ остаётся |
| Провайдер `Microsoft-Windows-TCPIP` | нет | **да** |
| Провайдер `Microsoft-Windows-Winsock-AFD` | нет | **да** |

Членство в группе `S-1-5-32-559` — разовая операция от администратора, после которой
приложение работает без повышения. В токене при этом **не появляется ни одной новой
привилегии** (`whoami /priv` до и после совпадают): право на создание сеанса даётся
членством в группе, а не привилегией, которую нужно включать.

## 1. Kernel-Network не подходит

Провайдер из плана отклоняется и после добавления в группу — это kernel-провайдер,
которому нужен администратор. Проверено отдельно: на уже созданном сеансе `logman update
trace ... -p Microsoft-Windows-Kernel-Network` отвечает «отказано в доступе», тогда как
`Microsoft-Windows-TCPIP` и `Microsoft-Windows-Winsock-AFD` на том же сеансе включаются
успешно. То есть отказ относится именно к провайдеру, а не к сеансу.

**Пункт плана надо исправить: провайдер — `Microsoft-Windows-TCPIP`.**

## 2. TCPIP отдаёт ровно то, что нужно фазе 4

Захват подтвердил наличие событий с полным набором полей:

| Событие | Что несёт |
| --- | --- |
| `1169` (UDP, отправка) | `Pid`, `ProcessStartKey`, `LocalSockAddr`, `RemoteSockAddr`, `NumBytes`, `NumMessages` |
| `1170` (UDP, приём) | то же самое |
| `1033` / `1017` (TCP, подключение / приём подключения) | `ProcessId`, оба адреса, `Status` |
| `1477` (сводка по TCP-соединению) | `RttUs`, `MinRttUs`, `MaxRttUs`, ретрансмиты, счётчики байт |

Событие `1169` — это и есть недостающая половина: **удалённый адрес UDP-потока с
привязкой к процессу и со счётчиком байт**. Все пять отправленных датаграмм и все пять
принятых нашлись в захвате с правильными адресами и правильным pid.

`ProcessStartKey` рядом с `Pid` — приятная неожиданность: он позволяет не перепутать
процессы при переиспользовании pid, что для долгой сессии мониторинга существенно.

**Оговорка:** номера событий принадлежат манифесту провайдера и между версиями Windows
меняться могут. Код обязан искать события по провайдеру и номеру, а отсутствие ожидаемого
номера переживать деградацией, а не падением.

## 3. Ключевое слово и уровень — это вопрос бюджета

Нужные события живут под `ut:SendPath | ut:ReceivePath` (`0x0000000300000000`). Проверялись
и отвергнуты: `ut:Endpoint`, `ut:Transfer`, `ut:TcpipEndpoint`, `ut:TxIoInfo` — событий
`1169`/`1170` не дают.

Уровень при этом решает всё. Одна и та же подписка, полторы секунды, машина почти без
нагрузки:

| Уровень | Событий общесистемно | Нужные события |
| --- | --- | --- |
| `0xff` (всё, включая `TcpIpPerPacket`) | **9845** | есть |
| `0x05` Verbose | 3824 | есть |
| `0x04` Informational | **617** | есть |

То есть `Informational` отсекает пер-пакетную телеметрию и сохраняет всё, что нам нужно, —
разница в шестнадцать раз.

Сколько это в бюджете. Одно событие `1169` приходится на один вызов отправки, а не на
пакет (`NumMessages` в захвате равен 1 при пяти отправках — пять событий). Бюджет CLAUDE.md
— 1 % одного ядра, то есть **10 мс процессорного времени в секунду**. Отсюда:

- измеренные ~400 событий/с на почти простаивающей машине укладываются с большим запасом
  при любой разумной реализации разбора;
- под нагрузкой (игра + Discord + браузер + фон системы) поток реалистично уходит к
  тысячам событий в секунду. Здесь всё решает **цена разбора одного события**: при разборе
  по закэшированной схеме (~1 мкс) 3000 событий/с стоят 0.3 % ядра, а при вызове `TDH` на
  каждое событие (десятки мкс) те же 3000 событий/с съедают бюджет целиком.

То есть узкое место — не количество событий само по себе, а наивный разбор. Тем не менее
фильтрация по идентификатору процесса на стороне ядра (`EVENT_FILTER_TYPE_PID` в
`EnableTraceEx2`) остаётся главным рычагом: при лимите в пять наблюдаемых приложений она
срезает поток до событий ровно тех процессов, которые выбрал пользователь, и снимает
вопрос о цене разбора вместе с зависимостью от фоновой активности машины. **Это не
доказанное условие «иначе не влезем», а способ не выяснять предел опытным путём на машине
пользователя во время матча.**

## 4. Побочная находка для фазы 7+

Событие `1477` несёт `RttUs`/`MinRttUs`/`MaxRttUs` по TCP-соединению — это пассивная
оценка RTT, которую стек считает сам. В PLAN.md пункт «Passive TCP RTT from the OS's own
estimates (Windows TCP eStats)» помечен как требующий повышения прав. **Через этот
провайдер повышение не требуется** — достаточно того же членства в группе. Пункт стоит
переформулировать, когда до него дойдёт дело; сейчас это только заметка.

## 5. Что доступно вообще без всяких прав

Проверено тестами из коммита `feat(platform): enumerate processes and read the connection
tables`: перечисление процессов, путь к образу выбранного процесса, таблицы TCP и UDP с
владельцем (IPv4 и IPv6). **Строка TCP несёт обе стороны соединения**, поэтому TCP-эндпоинты
обнаруживаются полностью без ETW. **Строка UDP несёт только локальный сокет** — даже после
`connect()`. Это и есть та дыра, которую закрывает событие `1169`.

## 6. Следствия для плана

1. Провайдер в пункте фазы 4 меняется на `Microsoft-Windows-TCPIP`, ключевое слово
   `ut:SendPath | ut:ReceivePath`, уровень `Informational`.
2. Фильтрация по pid на стороне ядра — не оптимизация, а условие соблюдения бюджета.
3. Деградация обязана быть честной и является **штатным** состоянием, а не краем: у
   пользователя без разовой настройки сеанс не откроется вовсе. UI в этом состоянии
   говорит, что видны только TCP-эндпоинты, и не выдаёт отсутствие UDP за отсутствие
   трафика.
4. Разовая настройка — добавление учётной записи в группу `S-1-5-32-559` — требует
   администратора и перевхода в систему. Приложение не должно делать этого само: оно
   объясняет, что произойдёт, и оставляет действие пользователю.
